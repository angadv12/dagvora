What a mutation does
Orchestrator calls scheduler→Check state→TaskGraph checks IDs + cycles→Write graph + state→Wake run() ↺
Every check runs before the first write, so a rejection leaves both stores exactly as they were. Only add_task wakes the loop; a new edge can only make work less ready.
add_task(spec) registers in TaskGraph and ExecutionState.
add_dependency(a, b) needs b PENDING or READY.
RUNNING, COMPLETED, or FAILED → TaskStartedError.
Both calls are synchronous on the event loop.
run() only pauses at asyncio.wait, so no mutation is seen half-done.
The scheduler stays the single writer without locks.


Allowed state changes
PENDING→READY→RUNNING→COMPLETED / FAILED
READY→PENDINGnew in Stage 3
The new move happens only when a dependency gives a ready task a prerequisite that hasn't finished, so READY still means every prerequisite is COMPLETED. The scheduler never leaves a task READY while it waits, so this applies only to state set up before run().


The diff, one piece at a time


Scheduler.add_task — one call, both stores
It checks the graph for the ID, registers it in ExecutionState, then adds it to TaskGraph. The last step cannot fail, so a duplicate ID raises DuplicateTaskError and changes nothing. The new task starts PENDING and goes through the normal readiness check.


Scheduler.add_dependency — the V1 policy
It reads both tasks' states first. A started dependent raises TaskStartedError. Then TaskGraph.add_dependency runs its existing missing-task, self-edge, and cycle checks, which already reject without writing.
A running task can still become a prerequisite. That changes the new dependent, not the running work.


The wakeup — inserted work starts now
While run() waits for workers, it also waits on a future that add_task resolves. Without it, a new task would sit until some worker finished. If every running worker was waiting on the new task, the run would hang.


READY → PENDING and TaskStartedError
One new legal transition in state.py and one new exception in exceptions.py, exported from dagvora. Nothing else in Stage 1 or Stage 2 changes.


Tests and docs
Fourteen new scheduler tests and two new state cases; 58 pass. Tests change the graph while tasks are running and use events for ordering instead of sleeps. Removing the wakeup, the state check, or the READY → PENDING move each makes a test fail. README and project context describe Stage 3.
